---
name: Frozen campaign plan/execute split
description: Why campaign allocation happens at a separate "plan" step from job creation/execution, and what "frozen" must mean end-to-end.
---

Rocket campaign execution is split into two idempotent steps: **plan** (validates readiness and freezes an immutable snapshot: routes with TPS/provider-cap evidence, selected templates, expanded mappings, and a deterministic per-contact allocation) and **execute** (creates persistent work from that frozen snapshot, safely re-callable after a partial failure or restart).

**Why:** separating allocation from job creation is what makes retries/restarts/idempotency simple. It also lets "frozen" be a real guarantee: once a plan exists, nothing else should be able to change what an already-planned/already-created unit of work does.

**How to apply — the frozen guarantee must reach every consumer, not just the snapshot table.** It is not enough to write an immutable snapshot; every downstream reader (rate limiting, template/mapping resolution, anything else that decides "what to send and how fast") must actually prefer the frozen values over the live, still-editable configuration tables they were copied from. The first version of this feature froze the snapshot correctly but left the runtime reading live config, so an edit made after planning (even while the campaign was paused) could silently change execution behavior — a live "immutable" plan whose consumers still read live tables is not actually immutable. Also: watch for plain CRUD/update endpoints on the same resource that don't route through the lifecycle/plan logic — they're an easy way to bypass frozen-state invariants entirely (e.g. writing a status field directly instead of going through the state-machine action that enforces it).

**How to apply — the transition that produces the snapshot must itself be serialized per resource, and every unit of work must point at its exact origin, not a mutable "current" pointer.** Concurrent transitions (e.g. two replans, or a replan racing an execute) can otherwise interleave and leave committed work stamped with a superseded snapshot while a newer one is marked active. Fix with two independent things: (1) a resource-scoped lock held across the *entire* multi-step transition (not just one internal transaction), so concurrent transitions for the same resource fully serialize cluster-wide; (2) persist the exact originating snapshot id on every unit of work, and always resolve against that stamped id — never against a global "currently active" lookup. If you hold an external lock across many round trips, route all of that operation's queries through the single locked connection rather than also drawing from the shared pool, or you double per-operation connection usage.

**How to apply — the snapshot must be self-sufficient, including the content of anything it references, or freezing IDs is not enough.** Freezing only identifiers (template id, mapping id) still leaves execution dependent on the live row behind that id — editing or deleting that row after planning (through its own normal, always-allowed management endpoint) silently changes or breaks already-planned work, and a cascading FK delete can null out or destroy the very column resolution was trusting. Freeze the actual content a downstream reader needs (e.g. a referenced template's body/components, not just its id), and validate eligibility against the plan's own frozen id list rather than a live "is this still selected" join. Reserve live lookups for genuine provider/compliance-side state that legitimately must be current (e.g. provider approval status), and treat destructive operations that would erase permanent audit/allocation history (not just editable config) as needing a fence/rejection instead, since freezing can't save data a cascade delete already erased.

**How to apply — every mutating transition on a lifecycle resource must share one lock, and every reader must recompute state fresh from inside it.** A resource-scoped lock only prevents races if *every* writer that touches lock-protected inputs takes it, not just the transitions that obviously "belong together" (e.g. plan+execute). Any sibling write path — other lifecycle transitions, and any CRUD/config-mutation endpoint that edits inputs the locked operation reads (selection, mapping, rate, or content tables) — must take the same lock before committing, or it can commit in the gap between the locked operation's separate reads and corrupt what gets frozen/decided. Also: never trust a pre-lock snapshot of the resource to decide the outcome — re-read fresh from inside the lock, since the snapshot can go stale while waiting for it.

**How to apply — retry-safe lifecycle actions must treat "already in the action's target state" as a no-op success, not a conflict.** A strict transition map that 409s on any state not in its allowed-from set breaks retries: a client resending a request after a lost response looks identical to an invalid call. Compare the current state against the action's settled/target state before rejecting, and short-circuit to success (without re-running side effects or writing a duplicate audit entry) when they already match.

**How to apply — a test that creates a real queued unit of work on a real "active" resource in a shared dev database races any live background worker polling that database**, not just the code under test; it will claim/process what it finds and corrupt assertions. Fix by setting the resource's existing "don't touch me" flag (e.g. a kill-switch/pause flag already checked by claim queries) before the work becomes visible, or by skipping real execution and inserting the unit of work directly in its already-claimed shape when the test only needs to exercise already-resolved state. If a test's own workers must claim through the unmodified production claim path (so the flag can't stay set for the whole test), toggling the flag off right before the test's own claim loop only shrinks — never eliminates — the race, because the live worker's claim attempt can itself be slow (e.g. a real outbound network call with fake test credentials), so it can still be "Processing" long after the test's own workers finish and assert. The only fully deterministic fix for that class of test is removing the live background worker from the picture for the run (stop its process/workflow before testing), not tightening the toggle window further.
