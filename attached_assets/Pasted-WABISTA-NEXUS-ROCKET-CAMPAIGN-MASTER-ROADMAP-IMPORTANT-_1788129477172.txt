==================================================

UP TO 1,000 TPS PER WHATSAPP NUMBER

Number B = 1000 TPS

Never exceed the actual provider-approved limit.

Effective TPS must be limited by:

+
Provider-approved TPS
+
Platform safety limit

Use the lowest applicable limit.

Requirements:

- Independent TPS for every number
- High-concurrency workers
- Efficient scheduler
- Fast durable queue
- Database optimization
- Connection pooling
- HTTP connection reuse
- Rate limiting
- Provider throttling detection
- Automatic backoff
- One slow number must not block other numbers

Do NOT create a fake TPS setting.

The actual sending engine must support the configured TPS.

Never claim 1000 TPS unless an actual controlled test proves it.

PHASE 5 — TPS OPTIMIZATION
==================================================

Current benchmark throughput must be treated as a bottleneck until the actual cause is understood.

Profile:

- Database queries
- Database locks
- Connection pool
- Queue throughput
- Job claiming
- Worker concurrency
- Scheduler
- Rate limiter
- Provider requests
- HTTP connections
- Settlement operations
- Metrics writes
- CPU
- Memory

Do not simply increase worker count.

Find the real bottleneck.

Optimize it safely.

After every optimization:

- Run regression tests
- Run controlled TPS test
- Compare before/after
- Check duplicates
- Check job loss
- Check crash recovery
- Check pause/resume


==================================================
PHASE 6 — MULTI-NUMBER SCALING
==================================================

Every WhatsApp number must operate independently.

Example:

Number A → 1000 TPS
Number B → 800 TPS
Number C → 500 TPS
Number D → 250 TPS

If Number A becomes throttled:

Number B, C and D must continue.

One number must never stop the complete campaign.


==================================================
PHASE 7 — QUEUE AND WORKERS
==================================================

Use a durable queue.

Jobs must survive:

- Worker restart
- API restart
- Queue restart
- Temporary database failure

Workers must support:

- Job claiming
- Job leases
- Lease expiry
- Retry
- Recovery
- Graceful shutdown
- Horizontal scaling

Multiple workers must never incorrectly process the same job.


==================================================
PHASE 8 — CRASH RECOVERY
==================================================

Test:

- Worker crash
- OS/process kill
- API restart
- Queue worker failure
- Database connection failure
- Provider timeout
- Provider throttling
- Crash after job claim
- Crash before job completion
- Pause during sending

Expected:

- No silent job loss
- No uncontrolled duplicate sends
- Expired jobs recover
- Retry works
- Campaign continues
- Final reconciliation is correct


==================================================
PHASE 9 — PAUSE / RESUME / KILL
==================================================

PAUSE:

- Stop new job claims
- Stop new sends
- Safely handle in-flight work
- Preserve queued jobs
- Preserve retry state

RESUME:

- Continue pending jobs
- Never resend completed jobs
- Preserve TPS limits

KILL:

- Stop new sends
- Safely reconcile jobs
- Mark campaign cancelled
- Preserve accurate analytics


==================================================
PHASE 10 — RETRY SYSTEM
==================================================

Retry temporary errors:

- Timeout
- Temporary provider error
- Network error
- Provider throttling

Use:

- Retry limits
- Backoff
- Retry scheduling

Permanent failures must not retry forever.

==================================================
PHASE 11 — STOP / SUPPRESSION
==================================================

If a user sends STOP or is suppressed:

Do not send future campaign messages.

Check suppression before final send.

Test STOP during an active campaign.

Expected:

Suppressed contact = no inappropriate subsequent campaign send.
